# 四项新能力设计：待办/纪念日、农历/节假日、长文摘要、娱乐抽签

> 面向：让鲸鲸从「会查资料」再往前一步——记住你的事、算得清日子、读得懂长文、能陪你玩。
> 状态：**设计，未实施**。依据：`src/services/capabilities.js`、`src/core/reminder.js`、`src/services/reminderService.js`、`src/adapters/links.js`、`docs/能力扩展规范.md`（2026-11-14）。

---

## 0. 先分清三类机制（这决定每个工具怎么落地）

不是所有「她该会的事」都塞进 `[[cap:]]` 注册表。按「谁发起」分三路：

| 类型 | 谁发起 | 走哪 | 现有例子 |
|---|---|---|---|
| **查资料/本地事实** | 用户问、她答 | 搜索/阅读/本地计算，结果注入提示词 | 天气、热搜、链接阅读 |
| **用户明确要她做** | 用户下指令 | 意图解析（规则 + 模型兜底）+ 命令 | 提醒（`提醒我…`）、`/提醒列表` |
| **她自主决定做** | 她自己判断 | `[[cap:<id>]]` 能力注册表 | 逛 B 站、写日记 |

本批四个工具分别落在：

| 工具 | 机制 |
|---|---|
| 待办 / 纪念日 | **用户明确要她做**（像提醒一样解析，不走 cap） |
| 农历 / 节假日 / 倒数日 | **本地事实**（纯计算，注入 prompt，不联网） |
| 长文摘要 | **查资料**（复用链接阅读 + 摘要指令增强） |
| 娱乐抽签 | **用户明确要她做**（命令式，走规则） |

### 0.1 四项都必须满足「能力闭环三要素」

每项能力都要能闭环（详见 `docs/能力扩展规范.md` §1.1）：**知道 → 调用 → 感知**。四项逐条对照：

| 工具 | ① 她知道会做 | ② 用户要求能调用 | ③ 调用后能感知 |
|---|---|---|---|
| 待办/纪念日 | 能力清单里加「记待办 / 记纪念日」一条 | 意图解析（规则+模型）+ 命令 `/待办` | 写进「最近做过」通道（不是只落 `todo.json`） |
| 农历/节假日 | 能力清单里加「算农历 / 查节假日」一条 | 命中 `lunar` intent 注入结果 | 本地计算，无副作用，**无需感知**（但它答过=感知） |
| 长文摘要 | 能力清单里加「读链接 / 总结长文」一条 | 发链接自动读 + 摘要指令 | 链接阅读结果本就会注入下一轮上下文 |
| 娱乐抽签 | 能力清单里加「抽签 / 骰子 / 塔罗」一条 | 命令 `/抽签` 等 | 抽签无持久副作用，**无需感知**；但命令结果即时回 |

> 关键提醒：**「需要感知」的是有持久副作用的能力**（待办、纪念日、B 站、日记这类「做了会改变状态」的）。
> 纯计算 / 纯随机（农历、抽签）本身不落状态，答过即感知，不必硬塞进「最近做过」。
> 反过来，**定时/主动调用**（B 站养鱼定时看、到点提醒）目前没进「最近做过」通道——这是规范 §1.1 已指出的
> 既有缺口，本批待办/纪念日的「到点提醒」这一支也要一并修。

## 1. 待办 + 纪念日

### 现状

提醒系统已经相当完整：`src/core/reminder.js`（规则解析 `parseReminder`）+ `chat.js` 的 `reminderFromModel`（LLM 兜底）+ `src/services/reminderService.js`（存储/到点触发/确认）。但它**只支持「一次性、到点」**——`parseWhen` 认「30 分钟后」「明天八点」，不认「每年」「先记着」。

### 要补的两块

**① 待办（无固定时间的备忘）**

- 触发词与提醒区分：提醒必须有 `提醒我/叫我/别忘` **且带时间**；待办是「帮我记一下 / 记着 / 别忘了」**不带时间**，或带「以后再说」。
- 数据：新建 `data/todo.json`（或复用 reminder 存一份 `at=null` 的条目）。建议独立 `src/services/todoService.js`，避免把 reminder 的「到点调度」逻辑搅进「清单」语义。
- 条目：`{ id, chatId, chatType, text, done, createdAt, finishedAt }`。
- 命令（规则，不调模型，像 `/提醒列表` 一样）：
  - `记一下 <事>` / `帮我记着 <事>` → 入列，回执「记下了：<事>」；
  - `/待办` 或 `待办列表` → 列出未完成，最多 5 条 + 序号；
  - `完成了 <序号>` / `第 N 条做完了` → 打勾，回执；
  - `忘了它 / 删掉 <序号>` → 移除。
- 意图解析：规则 `looksLikeTodo`（不含「提醒我」、不含可解析时间，但含「记一下/记着/别忘了/记下来」）；规则吃不准的走 `todoFromModel`（和 `reminderFromModel` 同款）。

**② 纪念日（每年重复 + 倒计时）**

- 触发词：「每年 3 月 8 日是我生日」「下个月 8 号是我们认识一周年」「5 月 20 号是我们的纪念日」。
- 数据：`reminderService` 条目加 `recur: 'yearly'` + 存「月-日」（`month`, `day`），`dueAt` 表示**下一次**触发时刻。到点触发后，把 `dueAt` 顺延到下一年（天然幂等，复用 reminder 的去重/ack）。
- 倒计时查询：「离 <X> 还有几天」→ 匹配纪念日列表，算 `nextOccurrence - now` 的天数，直接回答（规则，不联网）。
- 解析：`parseWhen` 不认「每年/纪念日」，需要在 `core/reminder.js` 加 `parseAnniversary`（抽「月-日」+ 事情 + 是否「每年」）。注意歧义：`8 号` 没月份 = 本月；`下个月 8 号` = 下月；「每年」才设 yearly，否则是一次性提醒。

### 能力 id / 命令归属

**不注册 `[[cap]]`**——待办/纪念日都是用户明确指令，不是她自主决定。走意图解析 + 命令，和提醒并列在 `chat.js` 的 `_decide` 提前退出分支里（提醒那一段的旁边）。

### 配置

- `features.todo`（默认开，管待办+纪念日两块，因为同一套存储）；
- 纪念日的「提前几天提醒」可留默认 0（当天提醒），不做 UI。

### 测试

- `tests/core/reminder.test.js` 补：`parseAnniversary`（每年/单次/无月份/下月）的边界；
- 新 `tests/todo.test.js`：入列/完成/删除/倒计时天数的纯函数；
- 保证「提醒我明天开会」不会被误判成待办，反之亦然。

## 2. 农历 / 节假日 / 倒数日

### 定位

纯本地计算，**不联网、不走 cap**，像天气一样「算好结果注入提示词」。问她「今天初几」「离过年还有几天」「今年中秋是哪天」时直接答。

### 数据与算法

- `src/core/lunar.js`：**零依赖**的阳历↔农历换算。需要内置一张农历日期表（1900–2100 的农历月信息，约 200 行 16 进制常量，公开算法），加十二生肖、二十四节气（天文近似公式）。
- `src/core/holiday.js`：法定节假日与调休。固定节气/农历节（春节、中秋、清明等）**可算**；国务院每年调休**必须数据**——内置一份 `data/holidays.json`（近 3~5 年，每年可手动追加），没有就退回「只报农历节日，不报放假」。

### 注入点

- 在 `searchService` 里加一个 `lunar` intent（和 `weather`/`hotlist` 并列），命中「初几/农历/属相/节气/过年/中秋/放假/离…还有几天」时走本地计算，不调 Bing；
- 或者更轻：在 `chat.js` 的提前退出分支加规则（像提醒），算好 `msg.lunarText` 注入。**推荐前者**——复用 search 的 intent/route 骨架，避免再造一个并行入口。

### 命令

- `今天初几` / `今年过年是哪天` / `离中秋还有几天` / `明年春节是几号` —— 都是自然语言，走 intent，不需要单独命令。

### 测试

- `tests/lunar.test.js`：已知日期的农历/节气/生肖回推（拿 2026 春节、2026 中秋等固定事实断言）；
- 闰月、跨年边界（腊月/正月）。

## 3. 长文摘要

### 现状（先泼冷水：大半已经能做）

`links.extractUrls` + `readLink`（`src/adapters/links.js`）能读网页正文；B 站视频能读字幕+热评。读到的正文通过 `msg.linkText` 注入 prompt，模型本就能「总结」。所以「发个链接让我总结」**基本可用**。

### 真正的缺口

1. **长正文注入不安全/被截**：`readLink` 可能抓到几万字，全塞进 prompt 会顶爆预算。缺「正文按预算截断 + 结构摘要」的中间层。
2. **摘要质量没约束**：没有专门提示词，模型可能复述而不是压缩，或丢关键数字。
3. **「贴一段文字，不一定是链接」的场景**：微信里常见「帮我把这段话总结一下」+ 一大段原文，走的是聊天正文，不经过链接阅读——这块其实是模型原生能力，加一句摘要指令即可。

### 设计

- 在 `readLink` 注入前加一层 `src/core/summarize.js`：把正文**按句切分 + 预算裁剪**（复用 `format.js` 的 `splitSentences`/整句丢的思路），超长时先给「前 N 字 + 尾 N 字」让模型知道「这是截断的」，不要假装读完。
- persona 加一条摘要指令：被要求「总结/摘要/说重点」时，压缩到要点（保留数字、人名、结论），并说明「这是截断/完整」。
- **不新建能力**：这是「阅读 → 注入 → 摘要」的增强，落点在 `links.js` 和 persona，不动 cap 注册表。

### 测试

- `tests/summarize.test.js`：长正文按预算整句截断、不切半句、标记「已截断」。

## 4. 娱乐抽签

### 定位

纯本地随机，零依赖，情绪价值。**放命令、不放 cap**——她不该主动抽签，只在被要求时。

### 内容

- `src/core/lottery.js`（纯函数，注入 rng 便于测试）：
  - `骰子`：`/骰子` 或「掷个骰子」→ 1~6；
  - `抽签`：`/抽签` → 内置签文库（约 32 支：上上/上/中/下，每支一句签文 + 一句解），随机；
  - `塔罗`：`/塔罗` → 22 张大阿卡纳随机一张 + 正/逆位牌意（各一句）。
- 签文/牌意内嵌在代码里（常量），不落 `assets/`、不做配置。

### 触发

`chat.js` 提前退出分支，规则匹配 `/骰子|掷骰|抽签|求签|塔罗|占卜`，直接回 canned 结果（不调模型，秒回）。避免「不务正业」：一天上限（复用 `capabilities` 的 maxPerDay 口径，或在 `features.lottery` 里设 `maxPerDay`）。

### 测试

- `tests/lottery.test.js`：注入固定 rng，断言骰子范围、抽签/塔罗非空、签文结构完整。

## 5. 落地顺序与工作量

| 顺序 | 工具 | 工作量 | 为什么先做 |
|---|---|---|---|
| 1 | 农历/节假日 | 小（一张数据表 + 纯函数） | 零风险、纯本地、即插即用 |
| 2 | 待办/纪念日 | 中（新存储 + 意图解析 + 命令） | 陪伴机器人第一性能力 |
| 3 | 娱乐抽签 | 小 | 低成本情绪价值 |
| 4 | 长文摘要 | 小（增强现有链接阅读） | 收益被高估，放最后 |

**硬约束**：零依赖（农历表、签文都内置）；每个行为改动配可复现测试；改完跑 `check-layers` / `privacy-scan` / `release-check`；用户可见行为变 `CHANGELOG.md` 补一段。
