# 鲸鲸私聊问题分析：反复问同一件事、以及「帮我挑晚餐」理解失败

- **分析对象**：`鲸鲸`（微信通道）与 `用户`（`（用户wxid已脱敏）`）的私聊
- **会话文件**：`data/memory/chats/（会话目录已脱敏）/`
- **数据范围**：2026-11-07 ～ 2026-11-15，共 340 条消息
- **重点时段**：2026-11-15（03:30 ～ 20:21）
- **分析方式**：只读分析，不修改代码、不修改记忆数据
- **结论口径**：基于 `messages.jsonl` 原文 + `people/*.json` 记忆卡 + `src/` 里实际生效的提示词与代码路径

---

## 0. 一句话结论

> 记忆系统把「还没兑现的事」设计成了**每轮必现的常驻背景**，却没有「这件事已经提过几次、什么时候算完」的状态；
> 而唯一防复读的机制只认**字面重复**，换一种说法就全部放行。
> 「酸菜鱼」那次属于同一机制下的次生问题：记忆里的常驻条目抢占了注意力，模型没有跟踪「谁让谁挑、谁吃」；
> 更糟的是，这次错误的理解随后被抽取器**写回长期记忆**，形成了闭环。

## 1. 现象还原

### 1.1 「欠语音」在同一天里被换了 4 种说法反复提

| 时间 | 鲸鲸原话 | 对方的反应 |
|---|---|---|
| 03:30 | 「能发啊，不过你还没醒吧？先把昨晚欠的语音还我。」 | 让她先发一条 |
| 14:01 | 「醒了啊，昨晚的语音还欠着呢」 | 没接 |
| 19:07 | 「点的啥，有汤没。说起来你还欠我语音呢」 | 转移话题 |
| 19:28 | 「酸菜鱼？哥哥今晚吃这个啊 ／ 对了，昨晚欠我的语音还记着吗」 | 「我可不欠你」 |

注意 19:29 他真的补发了语音（她回「听到了听到了，声音还挺好听嘛」）——**但记忆里的这条账并没有被关掉**（见 2.1）。

### 1.2 「汤」的问题在 17 分钟内被问了两次，被对方当场指出

```
19:07  鲸：点的啥，有汤没。说起来你还欠我语音呢
19:23  用户：没有
19:24  用户：你吃了吗
19:24  鲸：还没呢，我也想吃口热的。你点汤没有，别光吃干的     ← 又问了一遍「有没有汤」
19:24  用户：你不是刚问了
19:24  鲸：我这不是嘴快嘛，两次问的一样                    ← 被指出后才意识到
```

### 1.3 「帮我挑晚餐」的角色在下一轮就翻转了

```
19:24  用户：你吃了吗
19:24  鲸：还没呢，我也想吃口热的。你点汤没有，别光吃干的      ← A：她也没吃，想喝汤
19:27  用户：你想吃啥
19:27  鲸：想喝点汤，你帮我挑呗                                ← B：明确「替我挑」
19:27  用户：有啥可选的我看看
19:27  鲸：砂锅粥、老母鸡汤、酸菜鱼、馄饨面，你看哪个顺眼        ← C：主语已经变成「你（挑你）」
19:28  用户：酸菜鱼
19:28  鲸：酸菜鱼？哥哥今晚吃这个啊 ／ 对了，昨晚欠我的语音还记着吗  ← D：认定是「他吃」，并插入语音债
```

B 句是「帮我挑」，C 句变成「你看哪个顺眼」，D 句直接定性为「哥哥今晚吃这个」——**归属在 3 轮内翻转了两次**，鲸鲸没有察觉。

## 2. 根因一：未兑现的事被记忆系统做成了「常驻背景」

### 2.1 记忆里确实存着这条「未兑现」事实，而且永远不会自己结束

文件：`data/memory/chats/（会话目录已脱敏）/people/（人物卡文件已脱敏）.json`

```json
{
  "id": "pf_f230bca311",
  "text": "昨晚答应给鲸鲸发语音但还没兑现",
  "kind": "fact",
  "confidence": 0.9,
  "mentions": 101,
  "lastMentionedAt": 1794742242841,   // 11-15 19:30，最后一轮仍在刷新
  "superseded": false,                 // 从未被「取代」
  "deleted": false
}
```

同一文件里还有**两条内容几乎重复的未关闭线索**：

```json
{"id":"th_cb99e6faee","text":"昨晚答应鲸鲸的语音还没补上，鲸鲸在等 用户 补","status":"open"}
{"id":"th_6c4520bfac","text":"昨晚欠鲸鲸的语音还没补，鲸鲸说晚上讲但要求先补上，否则赖账","status":"open"}
```

这两条 thread 来自不同的 episode，描述的是**同一件债**——也就是说，光「语音债」这一个话题，在记忆卡里就有 **1 条 fact + 2 条 thread**，且全部是「未完成」状态。

**时机问题**：11-15 19:29 用户 发了语音、19:30 她回「听到了听到了」，债在现实里已经还了；但 19:30 的抽取（`ep_20261115_36`）只新增了「鲸鲸想让 用户 把语音内容再说一遍」这一条新 thread，**没有任何逻辑把旧的两条 thread 关闭、把 fact 标记为已兑现**。

代码依据：`src/memory/episode.js:168-187` 只做 `personCard.addThread(...)`，全文没有 `closeThread` / `supersedeFact` 的调用路径（thread 的 `closedAt` 只在极少数路径被写）。

### 2.2 记忆预算把这条「顶」到了必现位置

`config.json`：

```json
"memory": { "dialogueBudget": 10000 }     // 默认 5500
```

`src/memory/budgetPlan.js:100-109` 的 `cardCaps()` 会按 memory 预算等比放大条数上限：

```
scale = 10000 / 5500 ≈ 1.82
traits  = round(6 × 1.82)  = 11
偏好     = round(10 × 1.82) = 18
没聊完   = round(4 × 1.82)  = 7
事件     = round(5 × 1.82)  = 9
```

而 `src/memory/format.js:177-199` 的 `renderBody()` 是这样渲染的：

```
【这个聊天里的 TA】
- 性格：…
- 偏好：…；…；…（最多 18 条）
- 没聊完：…；…（最多 7 条）
【相关事件·索引】
【展开：…】
【这段之前聊过】摘要
```

该用户共有 34 条偏好，按 `confidence` 排序取前 18——`pf_f230bca311`（欠语音）正好落在里面；7 条 thread 里两条「欠语音」也都在里面；事件索引里还有 `ep31「互催语音」`、`ep33「鲸鲸催昨晚欠的语音」`、`ep08「欠下的语音尚未补」`。

**结果：每轮提示词里「语音债」会出现 4～6 次**（1 条偏好 + 2 条没聊完 + 多条事件 + 摘要里再提一次）。模型看到的不是「我提过一次」，而是一整屏都在说「他欠我语音、还没补」。

这直接解释了：为什么每轮都会重新提起、而且被提起时会挤进别的話題（19:28 那句「对了，昨晚欠我的语音还记着吗」就是插在吃饭话题里的）。

### 2.3 系统有「提了几次」的计数，却没有把它交给模型

`mentions: 101` 这个字段一直在累加（很多事实都是 100+），但 `format.js` 渲染时只输出 `clip(p.text, 40)` 的正文，**不输出 mentions、也不输出「最近一次提到是什么时候」**。

也就是说：系统知道「这条已经被提了 101 次」，但模型看不到这个信号，只能从原始聊天记录里去猜——而它猜不出来。

## 3. 根因二：提示词里没有私聊的「别重复问」规则

`src/persona/index.js`：

```js
// 716 行：这条规则只给群聊
const GROUP_HISTORY_RULE = '- 用前面聊过的内容接着聊：谁说过什么你记得，别重复问刚说过的事。';

// 1142 行：只在群聊分支被 push
lines.push(GROUP_HISTORY_RULE);
```

而私聊的上下文规则（766 行附近）是：

```js
'- 上面这些是你和对方之前的聊天记录，你记得谁说了什么、聊到哪了；接着往下说，别装失忆。'
```

方向恰好相反：**「别装失忆」在鼓励她引用过去**，而没有任何一条说「同一件事今天已经提过就别再提」。

私聊里唯一接近的约束是风格层的一句（`628` 行）：

```js
'- 有生活感：偶尔带一句自己当下的状态，但别每句都提，同一句也别重复。'
```

但这句管的是「自己的状态」，不管「重复追问对方」。

## 4. 根因三：防复读只认字面，不认语义

`src/pipeline/chat.js:2063-2085`：

```js
const heardList = this.recentHeard(decision);   // 对方最近 6 句
const ownList   = this.recentOwn(decision);     // 自己最近 4 句
const repeatsSomeone = heardList.some((h) => isEcho(text, h));
const repeatsSelf    = ownList.some((h) => isEcho(text, h));
if (repeatsSomeone || repeatsSelf) { /* 重写一次 */ }
```

`src/core/echo.js` 的 `isEcho()` 判定条件（节选）：

```js
if (a === b) return b.length >= 2;                                  // 完全相同
if (b.length >= 2 && a.startsWith(b) && a.length - b.length <= 3)   // 前缀
if (b.length >= 3 && a.includes(b) && a.length - b.length <= 3)     // 包含
if (a.length >= 4 && b.length >= 4 && …) {                          // 字符重合 ≥80%
  for (const ch of a) if (b.includes(ch)) same += 1;
  if (same / Math.max(a.length, b.length) >= 0.8) return true;
}
```

实际四句的字符重合度远低于 80%：

| 句子 | 与「先把昨晚欠的语音还我」的字符重合 |
|---|---|
| 昨晚的语音还欠着呢 | 低 |
| 你还欠我语音呢 | 低 |
| 昨晚欠我的语音还记着吗 | 中，但不足 80% |

所以**四次全部放行**。同理，「点的啥，有汤没」和「你点汤没有」也不算 echo。

## 5. 根因四：抽取器只增不关，还会把错误的理解固化下来

### 5.1 只增不关

`src/memory/episode.js`：episode 关闭时调用 `extract()` → 拿到 `facts / traits / threads / events` → 逐个 `addFact` / `addThread`。**没有任何一步是「检查这条旧 thread 是否已经完成」**。所以：

- 旧 thread 永远停在 `open`；
- 同一件事在不同 episode 里被反复抽成新 thread（`th_cb99e6faee`、`th_6c4520bfac` 就是这样重复的）；
- 事实的 `superseded` 只有在新事实**显式取代**时才会置位（比如「住在深圳」→「搬到北京」），「答应的事已经做完」不在此列。

### 5.2 错误的理解会被写成「事实」

「酸菜鱼」那次，19:28 之后抽取出的内容：

```json
{"id":"pf_97d171d69f","text":"今晚吃酸菜鱼","kind":"fact",
 "source":"msg_338","confidence":0.85,"mentions":1}
```

```json
{"id":"evt_ep_20261115_36_47d4f4","title":"酸菜鱼与补语音",
 "summary":"用户 说今晚吃酸菜鱼，鲸鲸提起昨晚欠的语音…"}
```

三处问题：

1. **归属错了**：对话里是「她让他帮她挑」，酸菜鱼是**替她挑的**（或至少归属未定），记忆里却写成 **用户 的**「今晚吃酸菜鱼」；
2. **来源指错**：`source: "msg_338"`，而 msg_338 是「我说了啥你听到没」，跟酸菜鱼无关——说明抽取时没有把事实对齐到原文；
3. **前后自相矛盾**：同文件里 `ep35` 的摘要写的是「鲸鲸说自己也没吃，想喝点汤，让 用户 帮她挑…**最后选什么还没定**」，而 `ep36` 直接写成「用户 说今晚吃酸菜鱼」。

从此以后，长期记忆里的前提就是「他在吃酸菜鱼」。**一次理解错误 → 变成永久事实 → 后续对话继续建立在错误前提上**，这就是「关联能力弱」的观感来源之一。

## 6. 根因五：模型配置放大了以上问题

`config.json`：

```json
"model": "deepseek-flash",
"thinking": false,
"temperature": 1,
"maxTokens": 1000
```

- `deepseek-flash`：能力/推理弱于 pro 档；
- `thinking: false`：不先想再答，直接出字，缺少「我刚才是不是已经问过」的自检；
- `temperature: 1`：采样随机性大，同一话题容易生成不同措辞（正好绕过字面复读检测）；
- `maxTokens: 1000` + 私聊 100 字上限：回复短，信息量少，重复同一句的成本更低。

在记忆块把同一件事强调 4～6 次的情况下，这个配置组合天然倾向于「顺着最显眼的那条说」。

## 7. 「酸菜鱼不理解」的逐层拆解

| 层次 | 发生了什么 | 证据 |
|---|---|---|
| 对话层 | 她先说「你帮我挑」，下一句却问「你看哪个顺眼」，把挑选主体让给了对方 | msg_329 / msg_331 |
| 语义层 | 场景里有两个「吃饭的人」：他在点外卖、她说自己也想吃；模型默认套用「他吃」框架 | msg_320 / msg_325 |
| 规则层 | 提示词没有任何「分清谁在做什么、谁让谁做什么」的要求 | `src/persona/index.js` 全文无此规则 |
| 注意力层 | 记忆块里「欠语音」反复出现，抢走注意力，最终插进吃饭话题 | 19:28 那句「对了，昨晚欠我的语音还记着吗」 |
| 记忆层 | 错误归属被写成 fact + event，后续继续用 | `pf_97d171d69f`、`evt_ep_20261115_36` |
| 模型层 | flash + 无思考 + temperature 1，缺少主语跟踪 | `config.json` |

## 8. 机制小结

```
                 ┌─────────────────────────────┐
                 │ 记忆卡：1 条未兑现 fact       │
                 │        + 2 条重复 open thread │
                 └──────────────┬──────────────┘
                                │ 不关闭 / 不取代
                                ▼
                 ┌─────────────────────────────┐
                 │ 每轮提示词（预算 10000）      │
                 │ 偏好 18 条 / 没聊完 7 条      │
                 │ → 「语音债」出现 4～6 次      │
                 └──────────────┬──────────────┘
                                │
        ┌───────────────────────┼────────────────────────┐
        ▼                       ▼                        ▼
  每轮重新提一次          挤占当前话题注意力         错误前提被固化
  （反复追问）            （酸菜鱼插话）            （记忆写错）
        │                       │                        │
        └───────────┬───────────┴────────────────────────┘
                    ▼
        防复读只查字面 → 换说法全部放行
                    ▼
        模型 flash + 无思考 → 无自检
```

**核心矛盾**：系统把「未完成事项」当成**常驻事实**，而不是**有生命周期的事件**；模型没有被赋予「这件事今天提过几次、算不算完」的状态，只能靠一屏重复提示去猜。

## 9. 可复现 / 可验证的方法

```powershell
# 1) 看这段私聊的原文
Get-Content C:\dev\dreaming-whale\data\memory\chats\（会话目录已脱敏）\messages.jsonl -Encoding UTF8
```

判断标准：

- `superseded` 仍为 `false`、`status` 仍为 `open` → 下一轮还会被注入；
- 若想验证「注入次数」，可临时把 `memory.dialogueBudget` 调回 5500（默认档），条数上限会降回 6/10/4/5，重复会明显减少——这本身就是「预算放大导致常驻条目变多」的反向验证。
