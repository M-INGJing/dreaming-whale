# 私聊消息防抖方案（对方分条连发）

> 状态：**已实施（2026-11-11）**。落地记录见文末 §9。
> 范围：桥接侧消息调度（`bridge/`），不涉及内核提示词与启动器 UI。

## 1. 现象

私聊里对方把一句话拆成几条发（例如「我今天」「去面试了」「有点紧张」），鲸鲸在**第一条**就回了，回复只覆盖前半句；后面两条又各自触发一轮，表现为「一句话回好几遍」或「打断对方」。

群聊很少遇到，因为群里有 @ 判定、接话窗口和冷却，私聊则是「来一条回一条」。

## 2. 根因：不是没合并，是合并在第一条就关窗了

链路上**已经有合并**，但它只合并「上一轮还没跑完时到达的消息」，管不到第一条。

1. `bridge/app.py:227-228` 创建了 `MessagePipeline`（按会话串行、跨会话并发）和 `MessageBatches`（按会话攒消息）。
2. `on_message`（`bridge/receiver_mixin.py:516`）：消息 `batches.push(chat, msg)`；只有 push 返回 True（该会话还没排 flush）时才 `pipeline.submit(chat, flush_chat, ...)`。
3. `MessagePipeline.submit`（`bridge/msg_pipeline.py:149`）：会话不在 `_running` 时，**立即** `_pool.submit(self._drain, chat)`，没有任何等待。
4. `flush_chat`（`bridge/receiver_mixin.py:494`）：`batches.take(chat)` 取走此刻攒下的消息，`split_runs` + `merge_text_batch` 合并成一次请求。

于是第一条到达时：`_pending` 里只有它自己，`submit` 立刻执行 → **单独回一条**。第 2、3 条要么在第一条处理期间到达（进 `_pending`，等这轮结束再合并），要么在回复后才到（再触发一轮）。`merge_text_batch` 只能合并「同一轮里攒下的」消息，对已经被单独处理掉的第一条无能为力。

一句话：**缺一个「等对方说完」的时间窗**。

## 3. 目标

- 私聊：对方连续发（间隔小于窗口）时，合并成一轮、只回一次。
- 不改：群聊行为、命令/管理员指令、图片/语音处理、跨会话并发。
- 延迟可感知但不烦人（默认 1.5 秒级）。

## 4. 推荐方案：桥接侧「固定防抖窗口」

### 4.1 机制

第一条私聊消息到达后，**先等 `debounceMs`（默认 1500ms）再取消息**：

- 窗口内到达的后续消息自然进入 `MessageBatches._pending`；
- 窗口结束时 `flush_chat` 的 `take` 一次性取走，`split_runs` + `merge_text_batch` 合并成一轮；
- **固定窗口**（从第一条算起），不因新消息无限延长——避免对方持续发导致永不回复。未来想更"懂人话"，可加一个「最长等待上限」后再升级成重置窗口（见 §5）。

### 4.2 落点（尽量小的改动）

| 文件 | 改动 |
|---|---|
| `bridge/msg_pipeline.py` | `MessagePipeline.submit(chat, fn, *args, delay=0.0)`；`_drain` 里在 `fn(*args)` 前 `time.sleep(delay)`。delay 只在该会话本轮第一次执行时生效（后续 flush 不重复等）。 |
| `bridge/receiver_mixin.py` | `on_message` 里按 `chat_type == 'private'` 计算 `delay = debounce_ms/1000`，传给 `submit`；命中命令/管理员指令时传 0（立即处理）。 |
| `bridge/app.py` | 读配置 `bridge.debounceMs`（默认 1500，0=关闭），传给 pipeline 或作为 `submit` 默认值。 |
| `bridge/config.py` | 新增 `DEBOUNCE_MS` 读取（`WHALE_DEBOUNCE_MS` 环境变量或 config 字段）。 |

### 4.3 配置

| 键 | 默认 | 说明 |
|---|---|---|
| `bridge.debounceMs` | 1500 | 私聊连发合并窗口（毫秒）；0 = 关闭，回到现状 |
| `batches.limit`（已有） | 8 | 单轮最多攒 8 条，超出丢最早（现有安全网） |
| `pipeline.per_chat_limit`（已有） | 8 | 单会话任务积压上限（现有安全网） |

### 4.4 边界

- **只对私聊**：群聊已有 @/接话窗口/冷却，且多人交替（张三说完李四接）不能并成一条，语义复杂，保持现状。
- **命令/管理员指令不参与**：`/reset`、`调整语态` 等应在 `on_message_inner` 识别，命中就跳过等待、立即处理。
- **图片/语音不合并**：`mergeable()` 只放行纯文本，非文本走原路径。
- **过期仍在入口判一次**：`on_message` 已有 `STALE_AFTER` 判断，防抖不改变「过期只在收到那一刻判一次」的语义。
- **会话独立**：`_pending` 按 chat 分，互不影响。
- **跨会话并发不变**：只在每个会话内加等待，不串行化不同会话。

### 4.5 与现有机制的配合

- `flush_chat` 取走消息后 `_flush_queued` 被清掉；处理期间新来的消息会再排一次 flush（现有逻辑），所以「窗口外的补充消息」仍会被处理，不会漏。
- `MessageBatches` 的丢最早、`MessagePipeline` 的积压上限都不动。

## 5. 备选方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 固定窗口（推荐）** | 第一条后等 1500ms | 简单、可预测、不会无限等 | 每条私聊固定延迟 1.5s |
| B 重置窗口 | 每条新消息重置计时，静默 1500ms 才发 | 更贴合「说完了」 | 对方持续发会一直等，必须加最长上限；实现更复杂 |
| C 语义判断 | 看句尾标点（「。」算说完） | 无延迟 | 微信用户很少用标点，误判多 |
| D 内核侧聚合 | 在 `/webhook/wechat` 前攒消息 | 不动 Python | HTTP 是同步语义，「多个请求共享一个回复」很别扭；SSE 与 JSON 两条返回都要改 |

推荐 **A**：改动最小、行为最可预测；稳定后可叠加 B 的「最长等待上限」做增强。

## 6. 验证方式

自检脚本 `scripts/bridge-pipeline-selftest.py` 补充用例（不需要微信、不连服务端）：

- 两条间隔 500ms → 一次 `flush_chat` 取到 2 条并合并；
- 两条间隔 2000ms（> 窗口）→ 两次 `flush_chat`；
- `delay=0` 时行为与现状一致；
- 群聊不传 delay，行为不变。

真机验证：

- 私聊连发 3 条短句 → 只回一次，内容覆盖三句；
- 私聊发 1 条 → 约 1.5 秒后回；
- 群聊 @ 她 → 与现在一致。

## 7. 风险与回滚

- **延迟 1.5 秒**：用户可感知，换来「看完了再回」。若嫌慢，可调到 1000ms。
- **一键回滚**：`bridge.debounceMs = 0` 等价于关闭，行为与现状一致。
- **worker 占用**：`_drain` 内 sleep 会占 worker（默认 4）。每会话同一时刻只有一个 flush，最坏 4 个会话同时等 1.5s 仍够用；若担心，可改用 `threading.Timer` 延迟入队，但复杂度上升，先不做。
- **只影响私聊**：群聊代码路径不变。
